# 工作日志：流量激增应急 + 数据补全

**日期**：2026-09-16 ~ 2026-09-17
**背景**：站点流量从日均 450 请求暴涨到 6 万+（来源主要是 Threads / Instagram 的站内浏览器，移动端为主）

---

## 一、线上事故：网站打不开（Error 1102）

### 现象
用户反馈网站打不开，页面返回 503。

### 排查
用 `wrangler tail` 抓到实时日志：

```
outcome: exceededCpu
exception: "Worker exceeded CPU time limit."
```

按天统计请求量：

| 日期 | 总请求 | 失败 | 失败率 |
|---|---|---|---|
| 09-13 | 948 | 21 | 2.2% |
| 09-14 | 422 | 0 | 0% |
| 09-15 | 446 | 0 | 0% |
| 09-16（到 11:20 UTC） | 63,393 | 650 | 1.03% |

关键证据是 CPU 时间分布：

| 状态 | CPU P50 | CPU P99 |
|---|---|---|
| success | ~9.2ms | ~280–350ms |
| exceededResources | **正好 10.0ms** | — |

失败请求精准卡在 10ms —— Workers Free 套餐的每次调用 CPU 上限。
Free 套餐的 10ms 不是硬砍，机器空闲时允许突发（所以 P99 300ms 也能跑通），
但节点繁忙时立刻执行。流量涨上来 → 竞争加剧 → 大面积 1102。

### 处理
1. 升级 Workers Paid（CPU 上限 10ms → 30s）—— 这是根治
2. 代码侧减 CPU：
   - 新增 `lib/session.ts`：首页一次渲染原本要调 5 次 `auth()`
     （layout 1 次 + 两个 TopRestaurants 各 1 次 + 两次 getFavoritedIds 各 1 次），
     每次都重新解一遍 JWE。用 React `cache()` 合成 1 次，且没有 session cookie 时
     完全不进 `auth()`
   - 补上 `public/favicon.ico`：之前 `public/` 是空的，每个浏览器默认发的
     `/favicon.ico` 都会进 Next.js 服务端渲染一个 404

### 结果
升级后连续 15 分钟约 2800 请求，**零 1102**。

```
11:20      92     4 ████   ← 最后一批错误
11:21     180     0
11:33     388     0
```

## 二、鉴定功能失效

### 现象
用户反馈「鉴定」用不了。

### 排查
直接调线上 `/api/verify`：

```
Google Maps API error: REQUEST_DENIED
This API project was not found.
```

换上新 key 后报错变成：

```
REQUEST_DENIED - API keys with referer restrictions cannot be used with this API
```

### 原因
API key 设了「网站（HTTP 引荐来源）」限制。站点是在 Cloudflare Workers
**服务端**调用 Google，服务端请求没有 Referer 头，必然被挡。

referrer 限制只对浏览器里跑的 Google API 有意义。本站没有任何浏览器侧的
Google 调用（照片走 `/api/photo` 服务端代理）。

### 处理
应用限制改为「无」，靠「API 限制 + 配额上限」保证安全。
另外确认了 `.env.local` 里的 `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`
**在代码里从未被引用**，没有打进前端，线上页面和所有 JS chunk 里都搜不到 key。
（建议删掉这一行，避免以后有人误用导致泄露。）

### 验证
端到端跑通：Google Places → MiniMax 分析 → 入库

```
店名    : 肉汁水餃子 餃包 新宿店
菜系    : northern (置信度 70)
正宗度  : japanese (30)
评论分析: 2 条 — ★5 flag(35) / ★5 remove(25)
```

AI 把两条只夸服务、没提菜品的五星评论分别标成 flag 和 remove，打假逻辑正常。

## 三、功能开发

### 首页「本周热门榜」
按最近 7 天详情页浏览量排名，横向滑动。

设计取舍：
- 按「餐厅 + 日期」聚合存储，不是一次浏览存一行 —— 行数只和餐厅数 × 天数相关
- 写入走 `ctx.waitUntil()`，响应发出去之后才落库，不占关键路径
- 榜单结果 KV 缓存 5 分钟，避免每次首页渲染都跑 `GROUP BY`
- 过滤爬虫 UA，否则会被 Googlebot 和链接预览带偏
- 冷启动兜底：数据不够时用高分店补齐
- 横向滑动用纯 CSS `scroll-snap`，不引入 JS 轮播

### 分享按钮
流量主要来自 Threads / Instagram，是「看到好店想转给朋友」的场景，
但之前没有任何分享入口。优先唤起系统原生分享面板，不支持时退回复制链接。

### about / privacy 页面
页脚一直链接着这两个页面，但它们根本不存在，点进去 404。
privacy 按代码实际行为写，不是套模板。

### 鉴定页公开最近鉴定记录
给 `restaurant_verifications` 加 `place_name` 列并回填历史记录 ——
店名原本只存在 `evidence_json` 里，而那个字段塞了完整评论正文，
列表每次渲染都去 parse 太浪费 CPU。

## 四、地图页：尝试后回退

### 背景
地图是早先在 `ac59f13` 里为了避开 Maps JavaScript API 的按次计费主动拆掉的，
当时改成了静态链接列表。这次想用免费方案重新做。

### 做法
MapLibre GL + OpenFreeMap 的免费 OpenStreetMap 矢量瓦片（无需 key、无调用上限），
彻底绕开 Google 的计费点。

### 过程中定位到两个真 bug
1. **maplibre v6 的 Web Worker 被 webpack 打包后路径失效** ——
   worker 靠 `new URL("./maplibre-gl-worker.mjs", import.meta.url)` 定位，
   打包后 `import.meta.url` 变成 `/_next/static/chunks/xxx.js`，
   而 webpack 不会把 worker 输出到那里，请求落到 404 页面拿回 HTML，
   报 `Failed to load module script: non-JavaScript MIME type text/html`。
   解法：把官方三个 ESM 产物原样复制到 `public/`，用带 `webpackIgnore` 的
   原生动态 import 加载。

2. **容器高度塌成 0** —— 容器写了 `absolute inset-0`，但 maplibre 会给这个元素
   加上 `.maplibregl-map` 类，其 CSS 是 `position: relative`，把 absolute 盖掉，
   `inset-0` 随之失效。

### 结果：回退
最终没能拿出「瓦片确实渲染出来了」的可信证据，且高流量页面已经连续几次部署白屏，
按用户要求回退成列表版。

**这里的教训**：几次「修好了」的判断建立在不可靠的测量上 ——
浏览器面板 viewport 是 0×0 导致尺寸数据全废；用 `readPixels` 读画布判断有没有
画出内容，而 maplibre 的 WebGL 上下文没开 `preserveDrawingBuffer`，
合成后读回来必然空白，这个方法本身证明不了任何事。

MapLibre 代码保留在仓库里（`components/RestaurantMap.tsx`、`scripts/copy-maplibre.mjs`），
地图页不再引用。下次要继续做，应该先在本地 dev 里用真实浏览器肉眼确认能出图，
再推线上。

## 五、CI 自动部署修复

### 现象
推送后没有任何新部署。

### 原因
Cloudflare Workers Builds 面板里构建命令是 `npm run build`、部署命令是
`npx wrangler deploy`，而 `wrangler.toml` 的 `main` 指向 `.open-next/worker.js` ——
纯 `next build` 不产出它，所以构建成功但部署必然失败。

### 两次尝试
1. 第一次把 `build` 改成 `opennextjs-cloudflare build` —— **改错了**，
   OpenNext 内部又会执行项目的 `npm run build` 去构建 Next.js，
   形成 `build → opennext → build` 无限递归，面板上表现为一直「正在构建」。
2. 第二次在 `open-next.config.ts` 里显式指定 `buildCommand: "npm run build:next"`
   把环打断。面板设置不用动。

### 结果
推送后 **120 秒**自动构建部署完成。

### 体检发现的数据缺口

| 字段 | 缺失 |
|---|---|
| 中文店名 | 218/228 (96%) |
| 营业时间 | 218/228 (96%) |

社交功能基本是空的：注册用户 4 人、收藏 1 条、用户自写评论 0 条。

### ① AI 补中文店名（零 Google 调用）
站点主打在日华人，但用户看到的全是日文原名，搜不到、记不住、没法转发，
中文 SEO 也做不起来。

新增 `scripts/fill-chinese-names.mjs`，只用已有的店名/地址/菜系交给 MiniMax 转写。
规则刻意保守：日文汉字转简体、英文品牌名原样保留、分店信息保留、
不创造与原名无关的名字。

```
海底撈火鍋 上野店       → 海底捞火锅 上野店
百味麺館               → 百味面馆
2100K冒鴨燙肚高田馬場店  → 2100K冒鸭烫肚高田马场店
MO-MO-PARADISE        → 保持不变
```

### ② 按车站找店（零 Google 调用）
在日本找店的心智单位是车站而不是行政区（用户想的是「池袋站附近」，不是「豊島区」）。

车站数据取自 OpenStreetMap 的 Overpass API（免费、无需 key），
离线算最近车站和步行分钟数（按日本不动产惯例 80m/分钟）。
刻意不用 Google 的距离接口 —— 那些按次计费，这件事完全可以离线算。

1551 个车站 / 228 家餐厅，步行距离中位数 173m：

```
池袋      43 家  平均 220m（步行 3 分钟）
新小岩     16 家  平均 376m（步行 5 分钟）
高田馬場    16 家  平均 175m（步行 3 分钟）
上野御徒町   13 家  平均  75m（步行 1 分钟）
```

分布和东京ガチ中華的实际情况吻合。

### ③ 营业时间 + 实时营业状态
**发现原来的同步根本不会采集营业时间** —— Google 请求的 `fields` 里没有
`opening_hours`，入库语句也没这一列。字段在 schema 里躺了几个月，96% 是空的，
页面也没有任何展示。

如果没先验证就跑全量刷新，会白烧 228 次配额还是拿不到数据。

补齐整条链路后，只存 `periods` 和 `weekday_text`，**不存 `open_now`** ——
那是拉取瞬间的快照，存下来必然过期并误导用户。营业状态按东京时区实时算，
处理跨夜营业。

### ④ 全量刷新
228 家各一次 Place Details 调用，一趟解决营业时间入库、刷新照片、重跑品类分类。

## 七、事故：刷新反而毁掉了部分数据

### 现象
刷新后品类和菜系不降反升：品类=其他 114 → 122，菜系=其他 49 → 70。

### 原因
228 家里有 **35 家 MiniMax 调用失败**，而代码里的兜底
`normalizeAiAnalysis(null)` 会返回 cuisine=other / dish=other /
authenticity=unknown / 摘要「暂无摘要」，这些占位值被当成正常分析写回数据库，
把原本正确的分类抹掉了。

### 处理
1. **堵住根因**：AI 失败改为返回 `aiAnalysis = null`，保存时走「不带 AI 字段」
   的那条 upsert，只更新 Google 原始数据，已有分析原样保留。
   宁可这次不更新，也不能用占位值覆盖真实数据。
2. **修复受损的 35 家**：新增 `scripts/repair-ai-analysis.mjs`，
   只读数据库里已有的评论重跑 AI，不调用 Google。

### 最终数据

|---|---|---|
| 缺中文名 | 218 | **0** |
| 缺营业时间 | 218 | **8** |
| 缺最近车站 | 228 | **0** |
| 品类=其他 | 114 | **101** |
| 菜系=其他 | 49 | **43** |

修完后比刷新前更好。剩下 8 家没有营业时间是 Google 本身就没有数据。

## 八、事故：一晚上产生约 1200 日元账单

### 现象
第二天早上收到账单。

### 原因
计数器记录的本月全部 Google 调用：

```
photo         2235 次   ← 大头，且仍在涨
details        234 次   ← 全量刷新本身
nearbysearch     6 次
textsearch       3 次
```

**两笔都是全量刷新造成的**：
- Details 234 次 = 刷新本身，带 `reviews` 属于 Google 最贵那档
- Photos 2235 次 = 连锁反应。`/api/photo` 的 R2 缓存键是 `photo_reference + 宽度`，
  刷新把 reference 全换成新的，**整个图片缓存立刻作废**，
  228 家店的图靠真实流量一张张重新下载

**更糟的是这一步完全没必要**：图片显示的问题在刷新之前就已经用
「R2 未命中时复用同一张图的其它宽度」修好了，零调用。

### 排查中的一次误判
看到 R2 `object_count: 781` 对不上 2235 次调用，一度判断「缓存坏了」。
实测 20/20 全部命中，缓存一直正常 —— 781 是 Cloudflare 的延迟统计，不是实际对象数。

### 处理
1. 立即把 `GOOGLE_API_MONTHLY_BUDGET` 压到 2235，**切断 photo 调用**
   （计数器冻结，未缓存的图退回占位图）
2. 加防呆：两条 upsert 都改成只在 `photos` 为空时才写入。
   需要强制刷新照片时走单独脚本，不要混在常规同步里

### 冻结期间实测剩余缺口（零成本探测）
```
抽样 25 家 × 详情页前 5 张图 @800
  已缓存  34%
  未缓存  66%
全站详情页图片 ≈ 1155 张，填满缓存还需回源 ≈ 758 次
```

## 经验教训

1. **先恢复可用状态，再查问题**。地图白屏时用户说了两次退回，都先去修了，
   结果高流量页面多坏了两轮部署。
2. **不可信的测量比没有测量更糟**。viewport 0×0 的尺寸数据、
   没开 `preserveDrawingBuffer` 的 `readPixels`，都会给出看似确定的错误结论。
3. **花钱的操作必须先小批量验证**。营业时间那次如果直接跑全量，
   会白烧 228 次配额还拿不到数据；1 家试跑就发现了字段没采集的问题。
4. **兜底逻辑不能是破坏性的**。AI 失败返回占位值并写库，一次批量刷新就毁掉几十家数据。
5. **缓存键的组成部分要当成不可变**。photo_reference 一变，整个 R2 缓存作废，
   等于重新付一遍下载费。
